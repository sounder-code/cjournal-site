# K-apt 일괄 데이터 파이프라인

## 운영 원칙

- 사이트 데이터의 기준은 K-apt 자료실이 매주 공개하는 정부 일괄 XLSX 파일이다.
- 현재 운영 단계에서는 공공데이터 OpenAPI를 호출하지 않는다.
- 기본정보, 면적정보, 관리비정보의 기준일이 모두 같을 때만 최신 데이터로 반영한다.
- 원본의 내용 정확성은 제공기관 기준으로 두고, 파이프라인은 파일 무결성·스키마·중복·결합률을 검증한다.

## 한 번에 갱신

```bash
npm run data:kapt
```

위 명령은 다음 순서로 실행된다.

1. K-apt 최신 게시물에서 기본정보·면적정보·관리비정보 XLSX를 내려받는다.
2. `data/kapt/raw/YYYYMMDD/`에 원본을 보관한다.
3. 세 파일을 단지코드로 결합하고 관리비부과면적으로 나눠 `원/m2` 단가를 계산한다.
4. 전국 검색용 인덱스와 시도별 상세 파일을 생성한다.

원본 파일은 용량이 크므로 Git에서 제외한다. 현재 원본 정보는 `data/kapt/raw/latest.json`에 기록된다.

## 개별 실행

```bash
npm run data:kapt:download
npm run data:kapt:bulk
npm run data:kapt:bulk:validate
```

이미 받은 원본을 다시 변환할 때는 `data:kapt:bulk`만 실행한다. 다른 원본 묶음을 사용할 때는:

```bash
KAPT_BULK_MANIFEST=data/kapt/raw/20260710/manifest.json npm run data:kapt:bulk
```

## 생성 파일

- `public/data/apartments/manifest.json`: 기준일, 최신 관리비 월, 행 수, 결합·중복 검증 결과
- `public/data/apartments/index.json`: 전국 단지 검색용 경량 인덱스
- `public/data/apartments/regions/*.json`: 시도별 단지 상세정보와 월별 관리비

시도 파일의 `f` 배열은 `manifest.json`의 `feeColumns` 순서를 따른다. 숫자 키를 사용한 이유는 전국 데이터를 브라우저로 전달할 때 파일 크기를 줄이기 위해서다.

## 배포 전 확인

```bash
npm run data:kapt:bulk
npm run data:kapt:bulk:validate
npm run typecheck
npm run build
```

`manifest.json`에서 아래 항목을 확인한다.

- `duplicateComplexes`, `duplicateFeeRows`, `areaConflicts`
- `feeRowsWithoutArea`, `feeRowsWithoutComplex`
- 직전 갱신 대비 `complexes`, `feeRows`의 비정상 급감 여부
- `sourceDate`와 `latestMonth`

전국 지도 마커에 필요한 좌표는 별도의 정부 주소 좌표 일괄 DB를 결합한다. 좌표가 준비되기 전에도 전국 단지 검색과 상세 데이터는 이 파이프라인 결과만으로 운영할 수 있다.

## 단지명 변경과 기존 주소

단지코드를 식별자로 사용해 직전 공개 데이터의 `s`(slug)를 유지한다. 신규 코드만 현재 이름으로 slug를 생성한다. 현재 이름은 `n`, 이전 공개 데이터에서 확인된 이름은 선택 필드 `an`(문자열 배열)에 보관한다. 별칭이 없는 단지에는 `an`을 쓰지 않는다. 기존 별칭과 직전 이름을 누적하고, 공백·중복·현재 이름을 제외하며 정렬해 반복 변환 결과를 안정적으로 유지한다. slug의 문구로 이전 이름을 추측하지 않는다.

`an`은 전국 인덱스, 검색 요약, 지역 상세, 지도 파일에 함께 전달한다. 단지 목록·지도 검색과 지도 자동완성에서 이전 이름도 검색되며, 상세 페이지에는 현재 이름과 구분하여 “이전 공개 자료의 단지명”으로 서버 렌더링한다. 검색엔진 순위는 보장하지 않는다. 배포 시 데이터 재수집 없이 코드를 바꾼 것만으로 과거 별칭이 생성되지는 않는다. 다음 정상 변환부터 직전 공개 데이터와 비교해 누적하며, 이미 사라진 이름의 복구는 확인 가능한 과거 원본·공개 기록을 별도로 검토해야 한다.

코드 누락과 공개 품질 조건 탈락은 기존 URL 보호 장치가 계속 차단한다. 이름 변경으로 기존 주소를 버리거나 품질 조건을 우회하지 않는다. `npm run test:regressions`는 임시 XLSX와 임시 출력만 사용해 이름 변경·별칭 누적·반복 변환·누락·품질 탈락을 검증한다.

## 갱신 지연 자료의 보존

기존 `q=1` 단지에서 최신 기본정보의 코드가 누락되거나(`basic-missing`), 최신 관리비 파일에 행이 없거나(`fees-missing`), 공개 조건을 충족하지 못하면(`quality-failed`) 직전 정상 상세 레코드 전체를 보존한다. 역사적 관리비 파일에 행이 남아 있어도 최신 관리비 파일에서 단지가 사라지면 지연 상태로 구분한다. 신규 단지의 불완전한 자료를 임의로 보충하지 않는다.

선택 필드 `st`는 마지막 정상 자료의 원본 기준일(`sourceDate`)·출처(`source`), 지연 최초 확인일(`since`), 최근 확인 원본 기준일(`checkedDate`)과 사유(`reason`)를 담는다. 지연이 반복되어도 정상 원본 날짜·실제 관리비 월·내용 수정일은 덮어쓰지 않는다. 정상 원본이 돌아와 공개 조건을 만족하면 `st`가 해제되고 현재 이름·내용이 다시 갱신된다. 기존 URL과 누적된 이름 별칭은 유지한다.

보존 자료는 검색과 상세 페이지에서 열 수 있으며 원본 기준일과 갱신 지연 안내를 표시한다. 상세 페이지의 Dataset 기준일은 실제 보존 자료를 따른다. 현재 비교군·지역 순위·중앙값·직접 비교에서는 보존 자료의 모든 월을 제외한다. 단지 수와 보관 행 수에는 포함되며 `retainedComplexes`와 `freshPublishableComplexes`로 따로 집계한다. `q`는 상세 페이지 존재 여부이며 최신 비교 가능 여부가 아니다.

보존 전에 기존 감소율 검사(단지 3%, 공개 대상 5%, 관리비 행 10%), 월 이력·기준일·중복·면적 충돌 검사를 수행한다. 보존은 기존 공개 대상의 0.5%(최소 1개), 최대 100개까지만 허용하며 이를 넘으면 쓰기 전에 중단한다. 원본 손상을 보존 레코드로 메우지 않는다. 공개 URL 검사는 보존 후에도 그대로 실행하고, 음수 총액/공용관리비 등 기존 후속 검증도 유지한다. 새 원본을 실제로 게시하려면 전체 검증을 통과해야 한다.

발행 후보 검사와 후속 일괄 검증은 `hasNegativeFeeAggregate`를 공유한다. 어떤 월이든 총 관리비 또는 공용관리비 합계가 음수인 기존 공개 단지는 `quality-failed`로 마지막 정상 자료를 보존한다. 세부 항목의 음수 정산값까지 일괄 차단하거나 음수를 0으로 바꾸지 않는다. 새 월이 양수여도 이전 음수 합계 행이 이력에 남아 있으면 지연이 유지되며, 원본 이력 전체가 조건을 충족할 때 보존 상태가 해제된다.
